# 保存予想をGitHub Pagesで見る

既存の7ページと保存予想を、同じGitHubリポジトリの `gh-pages` から配信する。公開ファイルには画面コード、合成テスト例、暗号化した表示用JSON、件数とハッシュだけを含める。平文の予想・結果、SQLite、鍵は含めない。

本人向けの閲覧URLは、Git外の私有ディレクトリの `owner-url.txt` に保存する。リンクのfragmentをブラウザ内で読み、AES-256-GCMを検証して既存の画面に渡す。リンクを知っている人は閲覧できる。URLなしのログイン認証を実装したという意味ではない。秘密リンクをIssue・PR・公開文書に貼らない。

閲覧用の鍵は、原本保存用 `RACE_AI_STATE_KEY` と異なる。この処理はActionsのキーを読み出さず、原本の暗号化状態・モデル・実行中workerも変更しない。表示時のモデル実行、収集、採点はしない。

## 作成

既に同期・照合した私有stateの内容SHAを指定する。出力先はGit外の別々のディレクトリにする。

```sh
python -m scripts.boat_saved_pages build \
  --state /private/pdca.sqlite \
  --source-sha <照合済みstateの内容SHA256> \
  --public-dir /private/pages/public \
  --private-dir /private/pages/owner
```

標準出力には公開用manifestとハッシュだけを出す。`owner/viewer.json` と `owner/owner-url.txt` は0600のまま保持する。通常はビルドごとに別の秘密リンクを発行する。既存リンクを維持する更新では、`--viewer-from /private/previous/owner/viewer.json` を追加する。既存の閲覧専用鍵と認証済みview_idを再利用し、暗号文・nonce・配信ファイルのSHAは更新する。V1の初回リンクとV2の更新形式の両方を検証する。原本保存用の鍵は使用しない。

配信対象はそのビルドの保存済みスナップショットであり、ライブ予想や継続自動更新とは表示しない。

## 結果と日予算の試算

「レース結果・収支」で取得済みの結果、保存Top8との一致、結果待ちを表示する。モデル・版・時点・履歴条件ごとに照合し、研究用の参考照合を正式な評価成績へ加算しない。結果だけ取得済みのレースも一覧に残す。

「保存Top8的中率」は的中数÷（的中数＋不的中数）を％表示し、結果待ち・中止・照合不可・未予想を分母へ入れない。「購入予定分の的中率」は日予算で配分したレースだけを同じ方法で集計する。分母0は「算出対象なし」。回収率は収支を確定できた購入額に対する払戻・返還の割合で、未確定額を別に示す。モデル比較表にも購入予定分の的中率・確定分回収率を表示する。

1日予算は初期値10,000円、100円単位で変更できる。締切順・同時刻はレースID順に、締切前の保存時刻が記録された完全なTop8へ各100円、1レース800円を配分する。残額不足は見送り、払戻・返還を再投資せず、翌日は予算をリセットする。検索や結果の有無で購入順を選び直さない。実購入台帳とは独立した試算である。

「1レース上限」を1,000円へ切り替えると、Top8の800円に追加200円を配分する。候補順位は追加配分の基準に使わない。選択原本と同じ時点・情報時刻・締切で、その原本の保存時刻までに保存されたモデルの支持数、履歴あり／なし両方の支持数を使う参考方式である。同一モデルIDの履歴違いを別モデルとして数えず、支持が同点なら組合せの数値順。異なるモデル2種類以上が支持する候補の上位2つへ100円ずつ、1候補だけなら200円を追加する。

追加の根拠がないレースは200円を未配分にする。日予算からは1レースの上限を先に確保し、未配分分を後続レースへ回さないため、1日1万円なら最大10レース。実配分額・未使用額・各券の支持数と配分理由は画面で確認できる。800円／1,000円の両方式をモデル比較表へ併記する。支持・履歴安定性は検証済みの信頼度や的中確率ではなく、事前の人気・オッズが保存されていない穴候補の自動判定はしない。

確定分の収支と未確定購入額を分ける。的中していても払戻額が不明なレースは、そのレースの実配分額全体を保留する。返還対象・同着時の個別払戻を確認できない場合も金額を推測しない。結果がないレースを不的中やゼロ円として集計しない。

## 配信

公開用manifestのSHAをビルド結果から固定し、初回だけ `--initialize` を使う。

```sh
python -m scripts.boat_saved_pages publish \
  --repo /path/to/RACE-AI \
  --public-dir /private/pages/public \
  --private-dir /private/pages/owner \
  --manifest-sha <ビルド結果のmanifest_sha256> \
  --initialize
```

2回目以降は `--initialize` を外し、独立して確認した `--expected-parent <gh-pagesのcommit>` を指定する。宛先は同じリポジトリの `gh-pages` 固定。既存の無関係なファイル、symlink、変更されたasset、平文ファイル、予期しない親commitを拒否する。検証したバイト列をそのままGitへ入れ、ネットワーク照会中のファイル変更で未検証データを混ぜない。

GitHub Pagesの設定はbranch方式の `gh-pages`・`/`。Actionsのcontents/pages/id-token権限を追加しない。Pages設定APIが拒否されたら、別の権限やプロバイダーで迂回しない。

公開成功は、PagesのHTTPS応答、配信されたasset・暗号文・manifestの一致、本人用リンクでの実予想表示まで確認する。コードCIやブランチへのpushだけで成功とは報告しない。

## 結果の同期と未照合理由

保存済みの結果成果物と、終了済み未照合レースの公式原文を私有journalへ追記し、元の予想・結果・採点履歴は変更しない。中止は選択された公式レースの専用表示と矛盾する着順・払戻がないことを確認し、全額返還とする。通常結果は6選手・着順・3連単の組合せと払戻を照合し、STの欠測や他券種の空欄だけで3連単を除外しない。

正式な採点の締切条件は維持する。画面の参考照合に限り、保存した公式原文でレース・6選手が一致し、締切差が60秒以内、予想保存が両締切より前、結果取得が両締切以降のものは差異を明示して比較する。中止ページの置換予定表は別に扱う。原本・結果ページの両時刻と差を表示し、原本を修正したり公式成績へ昇格させたりしない。

一覧と詳細には最終同期日時、照合理由、中止・返還、締切前、公式着順未公表、締切後未同期、情報不一致を区別して表示する。結果詳細カードの100件制限も外し、保存済みの全観測を確認できる。新しい結果の公表を推測せず、配信は確認した保存時点のスナップショットである。

## 保存予想の自動照合・サイト反映

既存の `boat-nationwide-ab-one-shot.yml` の結果保存・独立読戻しの後で、`scripts.boat_saved_view_feed` が暗号化した表示専用データを同一リポジトリの固定ブランチ `state/boat-saved-view` に追記する。既存の `contents: write` / `actions: read` を使用し、権限・巡回周期・公式GET上限を増やさない。表示の失敗は警告として保持し、原本保存や既存の収集処理は継続する。公式からすでに取得したHTMLは `RUNNER_TEMP` 内の0700ディレクトリへ0600で一時保存し、公開Artifactには入れない。取得時刻とSHAを照合して表示用に再解析し、ネイティブのST情報・原観測を置き換えない。

Pagesは60秒ごとに固定のGitHub raw配信先から最新manifestを読み、暗号文SHA、AES-GCM、表示ID、固定予想digest、世代を検証して結果・的中・日予算/1レース予算の収支を更新する。入力中は更新を待ち、候補・予算・モデル選択は維持する。鍵はURL fragment内に留まり、HTTPやブラウザ保存領域へ送らない。検証失敗・通信障害時は最後に検証できた結果を残す。

`audit/state/boat-saved-view-input.json` は表示鍵だけを既存のowner公開受信鍵に暗号化したbootstrapと、初期表示のcommit/cipher/予想digest、初回不足分を補う既存結果Artifactの固定SHAを参照する。`RACE_AI_STATE_KEY` はActions内でのみ使い、表示鍵でSQLite原本を復号できる構成にはしない。配信した過去の表示暗号文は削除しない。初回追いつきは不足/保留分だけを取得し、すでに全レース確認できた場合は期限付きArtifactを再取得しない。

対象はbootstrapで指定した保存済み予想・対象日である。別日の結果は混ぜず、将来日の予想取込や24時間の無期限スケジュールの完成を意味しない。自動反映は既存の結果収集処理の稼働と保存に依存する。締切差の参考照合や研究表示を公式的中率の根拠へ昇格させない。

保存結果の追いつきだけを実行するときは、head commitの件名を `saved-view:` で始める。この場合は同じworkflowの表示専用jobと独立したconcurrency groupを使い、公式収集jobを起動・待機列へ追加しない。実行中の公式収集を変更・停止せず、公開済みの暗号文と固定した過去Artifactだけを読み書きする。通常の収集workflowでは、確認済みの各round後の表示hookを使用する。収集側の上流ポリシー変更を本機能が承認・検証したという意味ではない。
