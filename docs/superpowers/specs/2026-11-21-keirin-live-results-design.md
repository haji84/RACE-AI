# KEIRIN result publication and diagnosis

## Owner request

Record the failed source purpose, HTTP status and stage without credentials; separate official finishing-order confirmation from payout-unit confirmation; compare prior successful source families without upgrading secondary agreement to official evidence; retain access refusal stops until the legitimate route is reviewed. Reflect published results automatically in the existing view, without ChatGPT scheduled tasks.

## Existing evidence and constraints

Use the existing GitHub Actions, encrypted Git state and owner display recipient. No new keys, paid services, permissions, model promotion, forecast rewrite, or provider-route bypass. The existing unknown-scope provider stop remains latched. Retain all result revisions. The fixed future-race trial does not become successful merely because offline tests pass.

## Chosen approach

The implementation uses a dedicated bounded observer workflow in the existing GitHub repository, plus a 30-second incremental reader in the existing encrypted owner view. It no longer queues behind forecast capture. Provider collection runs only through already approved source adapters and existing guards. Each admitted result batch is encrypted and published in the same processing iteration. Runtime observer cadence is 60 seconds while an eligible guarded job is active, with the existing eight-race request budget; this is a configured target, not a guaranteed publication-to-screen latency. Due current-day originals take priority, while older results get at most one tick in ten when no current-day original is waiting.

The observer lease is bounded to 540 seconds and ten ticks; five-minute GitHub schedules start or recover it during 08:00–23:59 JST. The prior result job is disabled so it cannot become a second poller. Queue delays, provider publication timing and a batch's acquisition time can all increase latency. No ChatGPT automation is created or resumed.

A notification/webhook implementation cannot be assumed because no legitimate provider push interface has been verified. Shortening cron alone does not update an already-open page and still permits GitHub queue delays. Introducing another host conflicts with the existing owner constraints. These are implementation decisions under the current request, not newly approved vendor integrations.

## Data boundaries

Safe diagnostics use fixed host/path-purpose enums, bounded HTTP numbers, observed timestamps and fixed failure stages/reasons. Never include URL query/form parameters, cookies, tokens, credentials, response bytes or exception text. A successful result remains available when the optional payout guide fails. Actual result and unit observation times stay independent.

The existing encrypted note feed gains result-only display packets. They cannot alter forecasts, cutoff times, stakes in frozen originals or the production model. Official status requires raw source reparse through the existing official adapters. Secondary agreement is labeled as reference only. A/B/C and adjusted A/B status are independent. Unknown-race updates are retained for joining but create no forecast.

Before result publication, a bounded read of the existing secondary-summary history compares the same race's retained Kdreams/netkeirin records with independently admitted official order and, only when confirmed, payout. Those older summaries retain URL/byte-hash/time receipts rather than raw HTML. The display therefore says 保存資料との照合; it does not claim fresh secondary retrieval or raw-source reauthentication. Missing/corrupt secondary records remain unavailable/unverified and never suppress the official result or alter scores.

Stable public result revision identifiers are domain-separated HMACs derived from the already configured and pinned owner private key's canonical DER representation. No new key is provisioned. Each result-only note also contains a fresh private random nonce inside its encrypted plaintext, preventing its public whole-plaintext checksum from becoming an offline guessing oracle. Existing forecast encryption and ciphertext are unchanged. A saved-only replay can publish authenticated archived order-only or full canary results without a provider request, runtime-clock backdating, or removal of the access stop.

The prior successful form history and current fixed-trial result path both reach the official `/sp/race` result page; this evidence does not support an assertion that all previous-day results were manually supplied PDFs. The old generic stop marker does not identify which URL or HTTP status failed. New purpose/host/path/status/stage diagnostics must not be retroactively presented as historical observations.

## Acceptance

- Offline regression demonstrates ordinary reCAPTCHA integration does not look like a challenge, while a true challenge/401/403/407/429 stops requests immediately.
- Failed source purpose/status/stage survives public-safe reporting.
- Official order remains visible if the payout unit is unavailable; monetary comparison remains held.
- The observer publishes before another tick, suppresses unchanged revisions, and performs zero source requests behind a persisted stop.
- The viewer fetches only appended encrypted entries and updates results without losing filters/selections. C pending never suppresses A/B.
- Existing ciphertext and prediction-model identities remain unchanged. Passing CI is reported separately from real provider execution.
